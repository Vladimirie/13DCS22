SRP, függvényhossz, paraméterszám, side effect – összefoglaló

SRP (Single Responsibility Principle)
Egy osztálynak vagy függvénynek egy és csak egy felelőssége legyen.
Ha egy metódus túl sokat csinál, azt le kell bontani külön logikai egységekre.

Függvényhossz
maximum ~ 20 sor
ha hosszabb: bontsuk alfüggvényekre

Paraméterszám
maximum 3 paraméter
ha több kell: csomagoljuk őket egy objektumba, vagy hozzunk létre egy request/config osztályt

Side effect kerülése
ne módosítsunk külső állapotot
függvény legyen pure, lehetőleg csak a bemenetekből számítsa ki a kimenetet

Tipikus tünetek, hogy SRP-t sértünk

egy metódus:
inputot dolgoz fel
üzleti logikát számol
adatot formáz
állapotot ment adatbázisba
→ legalább 4 külön felelősség

❌ sok if-else vagy switch logika
❌ sok paraméter
❌ hosszú metódusok
❌ mellékhatások tömkelege

❌ SRP-sértő példa (Java, de bármilyen nyelvre átültethető)
public class OrderService {

    public String processOrder(String rawInput) {
        // 1) input parsolása
        String[] parts = rawInput.split(";");
        String product = parts[0];
        int quantity = Integer.parseInt(parts[1]);

        // 2) üzleti logika
        double price = Database.getPrice(product);
        double total = price * quantity;

        // 3) mentés mellékhatás
        Database.saveOrder(product, quantity, total);

        // 4) output formázás
        return "Order: " + product + " x " + quantity + " = " + total + " USD";
    }
}

Mi a gond?

4 felelősség 1 metódusban
hosszú
side effect (adatbázis mentés)
3+ implicit paraméter (input, DB, stb.)

SRP-megfelelő, refaktorált verzió
1) Input feldolgozás külön osztályban
public class OrderInputParser {

    public OrderRequest parse(String rawInput) {
        String[] parts = rawInput.split(";");
        return new OrderRequest(parts[0], Integer.parseInt(parts[1]));
    }
}

2) Üzleti logika külön osztályban
public class OrderCalculator {

    public double calculateTotal(OrderRequest request) {
        double price = Database.getPrice(request.product());
        return price * request.quantity();
    }
}

3) Perzisztálás külön metódusban (side effect)
public class OrderRepository {

    public void save(OrderRequest request, double total) {
        Database.saveOrder(request.product(), request.quantity(), total);
    }
}

4) Formázás külön segédosztályban
public class OrderFormatter {

    public String format(OrderRequest req, double total) {
        return "Order: " + req.product() + " x " + req.quantity() + " = " + total + " USD";
    }
}

5) Fő szolgáltatás csak koordinál
public class OrderService {

    private final OrderInputParser parser = new OrderInputParser();
    private final OrderCalculator calculator = new OrderCalculator();
    private final OrderRepository repository = new OrderRepository();
    private final OrderFormatter formatter = new OrderFormatter();

    public String process(String raw) {
        OrderRequest req = parser.parse(raw);
        double total = calculator.calculateTotal(req);
        repository.save(req, total);
        return formatter.format(req, total);
    }
}

3. DIA — Mit jelent az SRP?

Single Responsibility Principle:

Egy osztálynak vagy függvénynek csak EGY felelőssége legyen.

Egyszerűbb karbantartás

Könnyebb tesztelés

Jobb újrafelhasználhatóság

Kevesebb mellékhatás

4. DIA — Mikor sérül az SRP?

Ha egy metódus „mindent is” csinál

Ha inputot dolgoz fel + üzleti logikát kezel + formáz + ment adatot

Ha nő a komplexitás, a sorok száma, az if-else logika

Ha a metódus nevét már nehéz megfogalmazni

5. DIA — Függvényhossz ajánlások

kevesebb hibát rejtenek

6. DIA — Paraméterek száma

max 3 paraméter

Ha több kell:

hozzunk létre konfigurációs osztályt

használjunk Request/DTO objektumot

csoportosítsuk logikai egységekbe

7. DIA — Side effect elkerülése

Side effect = amikor a függvény nem csak számol, hanem:

ír egy fájlba

adatbázist módosít

globális állapotot változtat

logol, külső API-t hív

Pure function ↔ biztonsággal tesztelhető, kiszámítható.

8. DIA — A tipikus "túl sokat csinál" metódus

Jellemző tünetek:

40–80 sor hosszúság

input parsing + üzleti logika + formázás + mentés

sok implicit függőség

nehéz unit teszteket írni

új fejlesztőnek "fekete doboz"
